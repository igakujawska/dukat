Swagger jest interfejsem dokumentacji API; frontend Angular to osobna część.

W Postmanie wybieram Authorization -> Basic Auth. W Swaggerze przeglądarka
może poprosić o Basic Auth przy wywołaniu chronionej operacji.
Konfiguracja OpenAPI nie definiuje jeszcze schematu zabezpieczeń dla

2. JAK DZIAŁA CAŁA APLIKACJA I SKĄD SPRING BIERZE OBIEKTY
========================================================

Docelowy przepływ:

Angular lub Postman
    -> HTTP: metoda + adres + ewentualny JSON
    -> Spring Security: sprawdzenie dostępu
    -> Controller: odebranie żądania
    -> Service: reguły biznesowe
    -> Repository: dostęp do danych
    -> JPA/Hibernate: mapowanie obiektów i zapytania SQL
    -> PostgreSQL: trwały zapis

Odpowiedź wraca przez backend jako HTTP, najczęściej z JSON.
GlobalExceptionHandler może przygotować odpowiedź dla błędu kontrolera.

API to zestaw uzgodnionych sposobów komunikacji, np.:
GET /api/accounts — pobierz konta.
POST /api/transactions — utwórz operację finansową.
GET /api/dashboard/summary — pobierz podsumowanie.

Spring Boot uruchamia i konfiguruje aplikację. Spring zarządza obiektami,
które zarejestrowano w jego kontenerze. Taki obiekt nazywam beanem.
Kontener Springa to mechanizm zarządzania obiektami w Javie; kontener
Dockera to odizolowane środowisko uruchomieniowe. To różne pojęcia.

Przykład z mojego projektu:

public TransactionController(TransactionService transactionService) {
    this.transactionService = transactionService;
}

Ten konstruktor mówi: aby powstał kontroler, potrzebny jest serwis.
Spring znajduje bean TransactionService i przekazuje go do konstruktora.
Serwis dostaje w podobny sposób repozytoria. To wstrzykiwanie zależności.
Przy pojedynczym konstruktorze nie muszę dopisywać @Autowired.
W obecnym kodzie @Autowired nie występuje.

private final oznacza, że pole jest prywatne, a przypisanej referencji
nie mogę później podmienić. final nie oznacza, że wskazany obiekt
lub zawartość bazy są niezmienne.

Samo umieszczenie klasy w pakiecie service/config/init jej nie uruchamia.
Potrzebna jest rejestracja, np. stereotyp komponentu lub metoda @Bean,
oraz odpowiedni mechanizm, który wywoła jej metody.

Encja JPA i bean Springa to różne role. Account jest encją zarządzaną
w kontekście trwałości przez JPA, a nie automatycznie singletonem Springa.


3. WSZYSTKIE ADNOTACJE: ZNACZENIE I ZASTOSOWANIE U MNIE
======================================================

Adnotacja to metadane oznaczone znakiem @. Określa informacje dla
kompilatora, Springa, JPA lub narzędzia testowego. Jej efekt zależy
od mechanizmu, który ją odczytuje. Nazwy i dokładne miejsca użycia
w moim kodzie są dodatkowo zebrane w indeksie na końcu.

START APLIKACJI I REJESTRACJA OBIEKTÓW

01. @SpringBootApplication
    Pakiet: org.springframework.boot.autoconfigure
    U mnie: DemoappApplication.
    Oznacza główną konfigurację aplikacji Boot, włącza automatyczne
    konfigurowanie oraz domyślne wyszukiwanie komponentów w jej pakiecie
    i podpakietach. main wywołuje SpringApplication.run(...).
    Dzięki położeniu klasy w com.example.demoapp Spring widzi m.in.
    controller, service, config i repository pod tym pakietem.
    Adnotacja nie dopisuje za mnie reguł biznesowych ani frontendu.

02. @Component
    Pakiet: org.springframework.stereotype
    U mnie: AuditLoggingAspect.
    Ogólny znacznik klasy, której obiekt ma zarejestrować Spring
    podczas skanowania. Obecna klasa audytu jest pusta, więc jej
    zarejestrowanie nie powoduje jeszcze logowania operacji.
    Nazwa z końcówką Aspect nie zastępuje implementacji aspektu.

03. @Service
    Pakiet: org.springframework.stereotype
    U mnie: dziewięć klas w service.
    Rejestruje komponent i zaznacza rolę warstwy biznesowej.
    TransactionService zmienia saldo, TransferService koordynuje przelew,
    a pozostałe serwisy mają zakres opisany w mapie plików.
    @Service nie tworzy automatycznie endpointu ani transakcji bazodanowej.

04. @Repository
    Pakiet: org.springframework.stereotype
    U mnie: osiem interfejsów w repository.
    Oznacza warstwę dostępu do danych. Implementacje moich interfejsów
    powstają dzięki Spring Data JPA i dziedziczeniu po JpaRepository.
    Nie są tworzone przez sam napis @Repository.
    Przy wykrywanych interfejsach Spring Data ta adnotacja zwykle
    nie jest konieczna; u mnie jawnie dokumentuje ich rolę.

05. @Configuration
    Pakiet: org.springframework.context.annotation
    U mnie: SecurityConfig, OpenApiConfig, SchedulingConfig,
    JwtConfig i RestClientConfig.
    Oznacza klasę konfiguracji Springa. Może zawierać metody @Bean
    lub włączać funkcje innymi adnotacjami.
    Pusta konfiguracja JWT nie oznacza działającego logowania tokenami.

06. @Bean
    Pakiet: org.springframework.context.annotation
    U mnie: OpenApiConfig.customOpenAPI i SecurityConfig.securityFilterChain.
    Wynik metody staje się obiektem zarządzanym przez Spring.
    Pierwsza metoda tworzy opis API, druga zestaw filtrów zabezpieczeń.
    Używam tego, gdy chcę samodzielnie skonstruować i skonfigurować obiekt,
    często z klasy należącej do biblioteki.

07. @EnableScheduling
    Pakiet: org.springframework.scheduling.annotation
    U mnie: SchedulingConfig.
    Włącza obsługę metod zaplanowanych do wykonania przez Spring.
    W kodzie nie ma jeszcze metod @Scheduled, więc sama ta konfiguracja
    nie nalicza płatności i nie wykonuje miesięcznych zadań.

OBSŁUGA HTTP

08. @RestController
    Pakiet: org.springframework.web.bind.annotation
    U mnie: wszystkie dziewięć kontrolerów.
    Rejestruje kontroler, którego wyniki metod są przekazywane do ciała
    odpowiedzi HTTP. Obiekty są najczęściej serializowane do JSON.
    U mnie ResponseEntity pozwala dodatkowo ustawić status odpowiedzi.
    Kontroler REST nie tworzy sam widoku HTML aplikacji Angular.

09. @RequestMapping
    Pakiet: org.springframework.web.bind.annotation
    U mnie: na klasach kontrolerów, np. /api/transactions.
    Ustala bazowy adres obsługiwanych żądań. Łączy się z adresem metody.
    DashboardController: /api/dashboard + /summary
    daje GET /api/dashboard/summary.

10. @GetMapping
    Pakiet: org.springframework.web.bind.annotation
    U mnie: metody pobierania danych w ośmiu kontrolerach.
    Przypisuje metodę Java do żądania HTTP GET.
    @GetMapping bez dodatkowej ścieżki korzysta z adresu klasy.
    Moje GET-y odczytują dane; TransferController nie ma GET-a.

11. @PostMapping
    Pakiet: org.springframework.web.bind.annotation
    U mnie: siedem metod tworzenia danych lub wykonania przelewu.
    Przypisuje metodę do HTTP POST. Oznaczenie POST nie zapisuje danych
    samo w sobie: zapis robi kod serwisu lub repozytorium.
    Status 201 jest u mnie ustawiany przez HttpStatus.CREATED;
    część POST-ów, np. przelew i użytkownik, zwraca obecnie 200.

12. @RequestBody
    Pakiet: org.springframework.web.bind.annotation
    U mnie: parametry siedmiu metod POST.
    Poleca odczytać treść żądania i zamienić ją na obiekt Java,
    np. JSON na CreateTransactionRequest.
    Nie uruchamia samo walidacji typu „kwota większa od zera”.
    Obecne DTO nie mają adnotacji ograniczeń, a parametry nie mają @Valid.
    Dodany starter-validation dopiero dostarcza narzędzia do walidacji.

13. @CrossOrigin(origins = "*")
    Pakiet: org.springframework.web.bind.annotation
    U mnie: wszystkie dziewięć kontrolerów.
    Określa reguły CORS używane przez przeglądarkę przy komunikacji
    z innego originu, czyli kombinacji protokołu, hosta i portu.
    Gwiazdka oznacza wszystkie originy, a nie tylko lokalnego Angulara.
    CORS nie zastępuje logowania. Współpraca z filtrami Spring Security
    i żądaniami preflight wymaga odpowiedniej konfiguracji CORS także
    w zabezpieczeniach. Postman nie egzekwuje CORS jak przeglądarka.

14. @RestControllerAdvice
    Pakiet: org.springframework.web.bind.annotation
    U mnie: GlobalExceptionHandler.
    Rejestruje wspólną obsługę wyjątków dla kontrolerów REST.
    Dzięki temu nie powtarzam tej samej obsługi błędów w każdym endpointcie.
    Nie przechwytuje automatycznie każdego błędu z każdego wątku aplikacji,
    a błędy w filtrach zabezpieczeń mogą być obsługiwane wcześniej.

15. @ExceptionHandler
    Pakiet: org.springframework.web.bind.annotation
    U mnie: trzy metody GlobalExceptionHandler.
    Wskazuje typ wyjątku, dla którego metoda przygotowuje odpowiedź.
    IllegalArgumentException -> u mnie HTTP 400 i komunikat.
    IllegalStateException -> u mnie HTTP 400 i komunikat.
    Exception -> u mnie HTTP 500 i ogólny tekst z wiadomością wyjątku.
    Konkretne statusy wynikają z mojego kodu ResponseEntity.
    Adnotacja nie ustala ich automatycznie na 400.

MAPOWANIE BAZY DANYCH — JAKARTA PERSISTENCE / JPA

16. @Entity
    Pakiet: jakarta.persistence
    U mnie: dziewięć klas modelu: Account, Budget, Category, Goal,
    Household, Membership, RecurringPayment, Transaction i User.
    Deklaruje encję, której stan może być mapowany do bazy przez JPA.
    Samo @Entity nie jest poleceniem CREATE TABLE.
    U mnie tworzenie/aktualizowanie schematu włącza ddl-auto=update.
    Encje potrzebują m.in. identyfikatora i konstruktora bez argumentów.

17. @Table(name = "...")
    Pakiet: jakarta.persistence
    U mnie: każda z dziewięciu encji, np. Account -> accounts.
    Podaje nazwę tabeli mapowanej przez encję. Nazwa klasy Java
    i nazwa tabeli SQL mogą się różnić.
    Nie jest adnotacją uprawnień ani instrukcją pobrania wszystkich wierszy.

18. @Id
    Pakiet: jakarta.persistence
    U mnie: pole id w każdej z dziewięciu encji.
    Oznacza identyfikator encji, odpowiadający kluczowi głównemu.
    Long w JpaRepository<Account, Long> musi pasować do typu tego id.
    To, że pole w Membership nazywa się userId, nie robi z niego @Id
    ani relacji @ManyToOne: jego znaczenie wynika z osobnego mapowania.

19. @GeneratedValue(strategy = GenerationType.IDENTITY)
    Pakiet: jakarta.persistence
    U mnie: obok @Id w dziewięciu encjach.
    Określa generowanie identyfikatora przy zapisie. Strategia IDENTITY
    korzysta z mechanizmu generowania wartości przez bazę.
    Nie muszę sama wyliczać kolejnego id przed utworzeniem konta.
    Wartości id nie muszą być ciągłe, bez luk.

20. @Column
    Pakiet: jakarta.persistence
    U mnie: 24 pola encji, z parametrami nullable i czasem unique.
    nullable=false opisuje kolumnę, która nie dopuszcza SQL NULL.
    unique=true opisuje wymaganie unikalności, np. nazwy konta lub emaila.
    To mapowanie i ograniczenia bazy przy generowaniu schematu.
    Nie zastępuje walidacji formularza ani żądania HTTP.
    Pusty napis "" nie jest tym samym co null. Dodatnia kwota
    i poprawny format emaila też nie wynikają z nullable=false.
    Pole bez @Column nadal może być zapisywane według domyślnych reguł,
    np. Goal.targetDate.

21. @Enumerated(EnumType.STRING)
    Pakiet: jakarta.persistence
    U mnie: Transaction.type i User.role.
    Zapisuje nazwę stałej enuma, np. EXPENSE albo ADMIN,
    zamiast jej numeru porządkowego. Przestawienie kolejności stałych
    nie zmienia wtedy znaczenia istniejących zapisów.
    Zmiana nazwy stałej wymaga uwzględnienia zapisanych danych.
    EnumType.STRING jest argumentem adnotacji, a nie osobną adnotacją.

22. @ManyToOne(fetch = FetchType.LAZY)
    Pakiet: jakarta.persistence
    U mnie: Transaction.account.
    Wiele transakcji może wskazywać jedno konto. W Javie trzymam
    referencję do Account; w tabeli transactions jest odwołanie account_id.
    LAZY oznacza żądanie odroczonego pobrania powiązanego obiektu;
    JPA traktuje ten tryb jako wskazówkę. Dostęp do account.getName()
    może spowodować dodatkowy odczyt danych.
    Poza aktywnym kontekstem trwałości odczyt niezaładowanej relacji
    może nie zadziałać. Nie jest to blokada współbieżnych zapisów.

23. @JoinColumn(name = "account_id", nullable = false)
    Pakiet: jakarta.persistence
    U mnie: również Transaction.account.
    Wskazuje kolumnę powiązania w tabeli transactions.
    account_id przechowuje identyfikator powiązanego konta.
    Wymaganie nullable=false mówi, że operacja musi mieć konto.
    Relacja jest opisana po stronie Transaction; nie trzeba mieć
    dodatkowo listy transakcji w Account, żeby ten kierunek działał.

TRANSAKCJE BAZODANOWE

24. @Transactional
    Pakiet: org.springframework.transaction.annotation
    U mnie: TransactionService.createTransaction i TransferService.executeTransfer.
    Wywołanie przez proxy Springa obejmuje metodę transakcją bazodanową:
    zmiany mogą zostać zatwierdzone razem albo razem wycofane.
    Domyślnie niewychwycone RuntimeException i Error powodują rollback;
    wyjątki checked nie zawsze, bez dodatkowej konfiguracji.
    U mnie ma to objąć np. odjęcie pieniędzy z jednego konta i dodanie
    na drugie. Wywołanie metody bezpośrednio z tej samej instancji
    zwykle omija proxy. Sama adnotacja nie rozwiązuje konfliktów
    równoczesnej zmiany salda — potrzebna byłaby odpowiednia strategia.
    Finansowa Transaction jest danymi o operacji. Transakcja bazodanowa
    jest mechanizmem spójnego wykonania zapisów. To odrębne pojęcia.

KOMPILATOR I TESTY

25. @Override
    Pakiet: java.lang
    U mnie: DemoDataLoader.run.
    Każe kompilatorowi sprawdzić, czy metoda rzeczywiście implementuje
    lub nadpisuje metodę typu nadrzędnego. Tutaj chodzi o run
    z interfejsu CommandLineRunner.
    Nie rejestruje klasy jako beana i nie uruchamia jej samodzielnie.

26. @SpringBootTest
    Pakiet: org.springframework.boot.test.context
    U mnie: DemoappApplicationTests.
    Uruchamia kontekst Spring Boot na potrzeby testów.
    Po poprawce webEnvironment=RANDOM_PORT uruchamia serwer na wolnym
    porcie, a properties nadpisują ustawienia bazy na testową H2.
    create-drop dotyczy tylko tej bazy testowej w pamięci.
    Nie zmieniłam ddl-auto=update dla zwykłego PostgreSQL aplikacji.

27. @Test
    Pakiet: org.junit.jupiter.api
    U mnie: dwie metody DemoappApplicationTests.
    Oznacza metodę wykonywaną przez JUnit jako test.
    Asercje sprawdzają status HTTP i zawartość odpowiedzi.
    Pusty test kontekstu został zastąpiony sprawdzeniami problemu Swaggera.

28. @Value("${local.server.port}")
    Pakiet: org.springframework.beans.factory.annotation
    U mnie: pole port w DemoappApplicationTests, dodane przy poprawce.
    Spring wpisuje do pola wartość właściwości z konfiguracji środowiska.
    Tu jest to faktyczny port serwera testowego. Nie wpisuję na stałe
    8082, więc test może działać obok aplikacji uruchomionej w IntelliJ.

Nie są adnotacjami: class, interface, enum, record, extends, implements,
private, final, static, public, new, throws, ResponseEntity, JpaRepository,
GenerationType.IDENTITY, FetchType.LAZY ani EnumType.STRING.
Nie ma też w moim kodzie @Valid, @Scheduled, @Aspect czy @Autowired.
Nazwy te mogą pojawiać się w wyjaśnieniach, ale nie należą do indeksu
adnotacji faktycznie użytych w źródłach.


4. KLASA, INTERFEJS, ENUM I RECORD — DLACZEGO MAM RÓŻNE TYPY
==========================================================

KLASA — dane i/lub zachowanie konkretnego rodzaju obiektu.
Account ma stan: nazwę, saldo i typ konta. TransactionService ma metody
wykonujące operacje. To oba rodzaje klas, ale o różnych zadaniach.
Klasa jest definicją typu; account znalezione w bazie to konkretna instancja.
Moje encje są klasami, bo opisują obiekty z tożsamością, stanem i mapowaniem JPA.
Serwisy i kontrolery są klasami, bo zawierają wykonywalną implementację.

INTERFEJS — umowa określająca, z jakich operacji można korzystać.

public interface AccountRepository extends JpaRepository<Account, Long>

Oznacza: repozytorium pracuje z Account, którego id ma typ Long,
i udostępnia m.in. findAll(), findById(), save(), count().
Nie piszę sama implementacji metod CRUD: obiekt repozytorium dostarcza
Spring Data. Dla findByName(String name) Spring Data interpretuje nazwę
metody i buduje odpowiednie zapytanie.
findByAccountId(Long accountId) w TransactionRepository odnosi się
do identyfikatora powiązanego pola account.

Repozytorium nie jest encją i nie jest pojedynczym wierszem w bazie.
Używa encji do dostępu do wielu wierszy. extends rozszerza umowę
JpaRepository. implements w DemoDataLoader oznacza dostarczenie
implementacji umowy CommandLineRunner.

ENUM — typ o zamkniętym zestawie wartości określonym w kodzie.
TransactionType: INCOME, EXPENSE.
Role: USER, ADMIN.
HouseholdRole: OWNER, MEMBER.
W TransactionType nie mogę dowolnie przypisać tekstu "WYDATEKK".
Enum nadaje się do niewielkiego zestawu opcji ustalonego przez program.
Kategoria tworzona przez użytkownika jest innym przypadkiem: jej wartości
mogą być danymi w tabeli, zamiast stałymi w kodzie.
Enum nie potrzebuje osobnego repozytorium, jeżeli jego wartości
nie są osobno zarządzanymi rekordami w bazie.
Role w modelu danych nie nadają automatycznie uprawnień Spring Security.

RECORD — zwięzły sposób zapisania klasy służącej do przenoszenia danych.
CreateTransactionRequest, TransactionResponse i CreateTransferRequest
to recordy. Kompilator tworzy m.in. konstruktor, metody odczytu,
equals(), hashCode() i toString(). Metoda odczytu to amount(), nie getAmount().
Pola składowe są final; to płytka niezmienność, a nie gwarancja
niezmienności dowolnych obiektów trzymanych wewnątrz.
Moje DTO nie mają własnej tożsamości i relacji JPA, dlatego record
jest dla nich wygodny. Nie oznaczam ich @Entity.


5. MODEL, REPOZYTORIUM, SERWIS, KONTROLER I DTO — PO CO PODZIAŁ
============================================================

MODEL/ENCJA: jak wyglądają przechowywane dane.
Transaction opisuje kwotę, datę, typ i konto operacji.

REPOSITORY: jak odczytać i zapisać te dane.
TransactionRepository oferuje zapis i wyszukiwanie transakcji.

SERVICE: jakie reguły obowiązują przy wykonaniu operacji.
TransactionService odczytuje konto, przelicza saldo i zapisuje transakcję.
To dobre miejsce na operacje, które łączą kilka repozytoriów.

CONTROLLER: jak klient wywołuje operację przez HTTP.
TransactionController odbiera POST i oddaje odpowiedź ze statusem 201.
Serwis może być użyty także przez zadanie w tle, bez kontrolera.

DTO: jakie dane wolno przyjąć od klienta lub mu odesłać.
CreateTransactionRequest przenosi accountId, a TransactionResponse
zwraca accountName. Dzięki temu odpowiedź nie musi być kopią encji
i nie trzeba serializować całego grafu powiązanych obiektów.

Nie każda rzecz wymaga kompletnego zestawu wszystkich warstw:
- Prosty odczyt kont korzysta teraz bezpośrednio z repozytorium.
- Dashboard oblicza wynik z istniejących danych i nie ma własnej tabeli.
- Przelew jest operacją na kontach, dlatego korzysta z AccountRepository.
- Enum jest zestawem stałych i nie ma osobnego repozytorium.
- Membership jest encją nawet bez własnego repozytorium. Brakuje jednak
  obecnie funkcji aplikacji, która zarządzałaby członkostwem.
- Dodawanie klasy przekazującej wyłącznie jedno wywołanie nie jest
  obowiązkiem frameworka. Warstwa ma służyć zrozumiałemu podziałowi zadań.

Przy prezentacji umiem powiedzieć: „Kontroler obsługuje HTTP, serwis
wykonuje przypadek użycia, repozytorium udostępnia zapis, a encja
opisuje dane. DTO opisuje kontrakt komunikacji”.

model/RecurringPayment.java — encja definicji płatności cyklicznej;

model/User.java — encja danych użytkownika; users. Ma username, password,

encję z polem password; do właściwej obsługi użytkowników potrzebne
są osobne DTO, hashowanie i integracja zabezpieczeń.

model/TransactionType.java — enum INCOME/EXPENSE, używany w Transaction
i DTO. TransactionService sprawdza INCOME, a w przeciwnym razie odejmuje kwotę.

model/Role.java — enum USER/ADMIN, zapisywany w User.role.

model/HouseholdRole.java — enum OWNER/MEMBER. Obecnie nieużywany

7. DWA PRZEPŁYWY KROK PO KROKU: WYDATEK I PRZELEW
================================================

A. DODANIE WYDATKU

Założenie: w bazie istnieje konto o id 1 i saldzie 1000.00.
Nie zakładam, że takie konto rzeczywiście już jest w mojej bazie.

POST http://localhost:8082/api/transactions
Authorization: Basic Auth z aktualnymi danymi uruchomienia.
Content-Type: application/json

{
  "description": "Zakupy",
  "amount": 50.00,
  "transactionDate": "2026-10-20",
  "category": "Jedzenie",
  "type": "EXPENSE",
  "accountId": 1
}

1) Security sprawdza uwierzytelnienie.
2) @RequestBody zamienia JSON na CreateTransactionRequest.
3) Kontroler wywołuje TransactionService.createTransaction.
4) @Transactional otwiera lub dołącza transakcję bazodanową.
5) findById wyszukuje konto. Optional opisuje możliwość braku wyniku.
6) Ponieważ typ to EXPENSE, kod odejmuje 50.00 od salda.
7) Repozytoria zapisują konto i nową encję Transaction.
8) mapToResponse tworzy DTO odpowiedzi.
9) Po udanym zakończeniu transakcja jest zatwierdzana; błąd może
   spowodować rollback. Moment wysłania SQL zależy też od JPA/flush.
10) Kontroler zwraca HTTP 201 z JSON. Oczekiwane saldo to 950.00.

BigDecimal.add/subtract zwraca nową wartość. Samo account.getBalance()
.subtract(amount) bez przypisania/setBalance nie zmieni salda konta.
LocalDate przechowuje datę bez godziny i strefy czasowej.

GET /api/transactions pobiera listę, stream().map(...) zamienia każdą
encję na DTO, a toList() zbiera wyniki. this::mapToResponse to referencja
do metody mapującej. Obecny kod nie dodaje stronicowania ani filtra.

B. PRZELEW MIĘDZY KONTAMI

POST /api/transfers z sourceAccountId, targetAccountId, amount, description.
TransferService sprawdza, czy konta są różne i istnieją, oraz czy saldo
źródłowe jest wystarczające. Następnie zmienia oba salda i je zapisuje.
Nie potrzebuje osobnego TransferRepository, bo aktualnie nie istnieje
encja Transfer do zapisania. Korzysta z AccountRepository.
Przelew nie dopisuje dziś wpisów do transactions, więc sam odczyt tej
tabeli nie pokaże pełnej historii zmian salda.


8. CO JEST GOTOWE, A CO NA RAZIE TYLKO ZAPLANOWANE
================================================

Własna nazwa klasy, obecność encji, beana i endpointu to różne etapy.
Przykład: zapis RecurringPayment jest gotowym fragmentem CRUD,
ale automatyczne wykonanie płatności cyklicznych nie jest gotową funkcją.

Konkretne różnice w obecnym kodzie, które warto umieć wskazać:

- JWT, integracja z NBP, rozliczenia gospodarstwa i audyt są szkieletem.
- Prognoza 2500.00 jest stałą demonstracyjną, nie wyliczeniem.
- Dashboard liczy rekordy, nie sumuje wartości finansowych.
- Role encji User i HouseholdRole nie sterują teraz dostępem do danych.
- Konta i inne rekordy nie są ograniczone do bieżącego użytkownika.
- Kategoria jako String nie jest powiązana z tabelą categories.
- Membership nie ma obecnie mapowania relacji, roli członka i obsługi API.
- DemoDataLoader nie jest beanem, więc sam się nie wykona.
- Brakuje walidacji wymaganych i dodatnich wartości w DTO.
  Szczególnie ujemna kwota przelewu mogłaby odwrócić kierunek zmiany sald.
- @Transactional daje wspólną granicę zapisu, ale nie zastępuje
  zabezpieczenia przed utratą zmian przy równoczesnych operacjach.
- UserController zapisuje i zwraca pole password. To nie jest kompletna
  implementacja kont użytkowników i bezpiecznego logowania.
- W bazie są mechanizmy tworzenia schematu Hibernate, ale plik
  db/migration/V!_init.sql jest pusty. Nie ma zależności Flyway.
  Sam katalog db/migration nie oznacza działających migracji.

Nie trzeba naprawiać całego tego zakresu, żeby zrozumieć przyczynę
błędu Swaggera. Na prezentacji należy jednak zgodnie ze stanem kodu
oznaczać funkcje jako gotowe, częściowe albo planowane.


9. NARZĘDZIA, KONFIGURACJA I KRÓTKIE ĆWICZENIA

Java — język backendu. Spring Boot — uruchomienie i konfiguracja backendu.
Spring MVC — obsługa HTTP. Spring Data JPA — repozytoria.
JPA — standard mapowania danych. Hibernate — jego używana implementacja.
JDBC — komunikacja Java z bazą; sterownik PostgreSQL jest już w pom.xml.

Po uporządkowaniu pom.xml projekt korzysta ze starterów webmvc, aspectj,

security-test już go dostarcza. DevTools ma runtime i optional=true;
optional zapobiega przekazywaniu go jako zależności kolejnym projektom.
Plugin Spring Boot domyślnie pomija DevTools podczas pakowania.
Wersja springdoc jest ustawiona osobno w properties jako springdoc.version,
ponieważ nie jest zarządzana przez parent Spring Boot.

Docker — uruchamia bazę w kontenerze na podstawie obrazu postgres:15.
docker-compose.yml — opis usługi db, portów, danych logowania i wolumenu.
5433:5432 oznacza port 5433 komputera -> port 5432 kontenera.
Wolumen dukat_postgres_data utrzymuje dane niezależnie od życia
pojedynczego kontenera. Nie trzeba usuwać danych do naprawy springdoc.

Postman — klient HTTP do wysyłania GET/POST i odczytu statusów oraz JSON.
Swagger UI — dokumentacja API z możliwością wywoływania operacji.
OpenAPI — format opisu API. springdoc — biblioteka budująca ten opis.
Żadne z tych narzędzi nie zastępuje reguł biznesowych backendu.

PostgreSQL — serwer bazy danych. pgAdmin — program do pracy z tym serwerem.
SQL — język zapytań. Terminal — miejsce uruchamiania poleceń narzędzi.
IntelliJ — środowisko pracy z kodem i uruchamianiem Javy.

application.properties ustawia m.in.:
- server.port=8082: port HTTP backendu;
- spring.datasource.url: adres połączenia JDBC do bazy;
- ddl-auto=update: aktualizację schematu przez Hibernate;
- show-sql=true: wypisywanie SQL w logu.

HTML/CSS opisują strukturę i wygląd interfejsu. Angular organizuje jego

W tym katalogu projektu nie znaleziono obecnie źródeł frontendu.

PYTANIA DO POWTÓRKI — ODPOWIEDZ WŁASNYMI SŁOWAMI

1) Dlaczego HTTP 200 z [] może oznaczać poprawnie działający endpoint?
   Bo lista w bazie może być pusta; sukces nie wymaga istnienia rekordów.
2) Dlaczego poprawny start aplikacji nie gwarantuje działania Swaggera?
   Część kodu i integracji jest wykonywana dopiero po żądaniu HTTP.
3) Dlaczego nie dopisuję konstruktora ControllerAdviceBean do swojego kodu?
   Błąd dotyczy zgodności bibliotek, a nie brakującej metody mojej klasy.
4) Dlaczego TransactionService ma dwa repozytoria?
   Operacja obejmuje konto i zapis historii finansowej.
5) Dlaczego TransferService nie ma własnego repozytorium przelewów?
   Obecnie zmienia konta i nie ma encji Transfer.
6) Dlaczego Category jest encją, a TransactionType enumem?
   Kategorie mogą być danymi, a typy operacji są zamkniętym zbiorem w kodzie.
7) Dlaczego User z tabeli nie może automatycznie zalogować się przez Basic?
   Brakuje integracji UserRepository z mechanizmem uwierzytelniania.
8) Dlaczego @Column(nullable=false) nie sprawdza dodatniej kwoty?
   Zakaz NULL i reguła „większe od zera” są innymi ograniczeniami.
9) Dlaczego DemoDataLoader nie tworzy konta podczas startu?
   Implementuje umowę runnera, lecz nie został zarejestrowany jako bean.
10) Czym różni się finansowa transakcja od @Transactional?
    Pierwsza jest danymi domeny, druga granicą spójnego wykonania zapisów.
11) Dlaczego rekord w tabeli categories nie ogranicza tekstu category w Transaction?
    Nie ma między nimi obecnie relacji ani odpowiedniej walidacji.
12) Jakie testy potwierdzają dzisiejszą poprawkę?
    HTTP 200 i zawartość OpenAPI oraz dostępność strony Swagger UI.

Ćwiczenie 1: narysuj przepływ POST /api/transactions i przy każdym kroku
zapisz nazwę klasy z kodu oraz typ danych wejścia i wyjścia.
Ćwiczenie 2: odszukaj wszystkie adnotacje w Account i powiedz, co stanie

Ćwiczenie 5: znajdź przykład każdej postaci: class, interface, enum,
